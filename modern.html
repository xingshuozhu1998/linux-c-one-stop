一、建立五层心智模型

  1. C 语言规则：源码表达的值、类型、对象生命周期和未定义行为，首先由所选 C 标准约束。C23 是现行标准；本书主体按旧标准编写，本项目先显式用 C17 复现。标准版本与编译器支持是两件事，不能以一次编译成功代替标准判断。参见 WG14 标准项目清单。
  2. 编译工具链：预处理、编译、汇编、链接逐步把源码变成目标文件和可执行文件。gcc -E、-S、-c分别留下中间结果；Make 根据依赖关系决定是否重建。参见 GCC 阶段选项和 GNU Make 手册。
  3. ABI（应用二进制接口）与 ELF（可执行与可链接格式）：目标平台规定类型布局、寄存器传参和机器码约定；ELF 文件保存符号、节及装载信息。看见同一段 C 在旧书和本机产生不同汇编，先核对 32/64 位 ABI 和编译选项。参见 ELF 规范与 x86-64 ABI。
  4. 运行库与内核：printf 属于 C 库接口，read 是 POSIX 接口，Linux 内核再提供系统调用。FILE *、文件描述符、内核打开文件对象是相关但不同的层次；线程和 socket 也要问清库接口与内核对象各是什么。参见 glibc 手册和 POSIX.1-2024。
  5. 容器边界：本容器固定 Ubuntu 24.04 的用户态工具和库，工作目录通过绑定挂载与主机共享；容器仍使用主机 Linux 内核。观察系统调用、调度和文件系统时，要区分镜像提供的用户态与主机提供的内核。参见 Docker 容器说明。

每次遇到不理解的现象，依次问：源代码属于哪一版 C？编译器怎样翻译？目标 ABI 是什么？调用落在哪个库或内核接口？容器和主机各提供了什么？这条因果链是后续理解 AI 基础设施中内存分配、数据搬运、并发执行和性能剖析的起点。

二、进入容器并完成第一轮实验

在主机打开 http://127.0.0.1:18765/index.html，或通过公开在线镜像阅读原书；进入容器后，/workspace 就是本项目目录：

docker exec -it zhuxs_linux_c bash
cd /workspace
pwd
gcc --version
clang --version
uname -m
getconf LONG_BIT

本机实测为 GCC 13.3、Clang 18.1、glibc 2.39、x86-64 与 64 位 long。容器中的 uname -r 报告的是主机内核。包更新或重新构建后，请以命令输出为准。

先在容器中另建个人练习目录；编译产物也会保留在主机目录中。下面的第一个程序同时验证编辑、编译、运行三步：

mkdir -p practice
cd practice
cat > hello.c <<'EOF'
#include <stdio.h>
int main(void) { puts("hello, C"); return 0; }
EOF
gcc -std=c17 -Wall -Wextra -Wpedantic -g -O0 hello.c -o hello
./hello
clang -std=c17 -Wall -Wextra -Wpedantic -g -O0 hello.c -o hello-clang
./hello-clang

两次运行都应输出 hello, C。-std=c17 明确语言版本，-g -O0 方便按原书使用 GDB（GNU 调试器）单步观察。GCC 13 在本容器中尚不识别正式拼写 -std=c23，可用 -std=c2x 观察其部分 C23 实现；Clang 18 接受 -std=c23。两者均不应被假定完整实现了 C23，具体特性应查 GCC和 Clang状态表。

把一个程序沿编译链展开：

gcc -std=c17 -E hello.c -o hello.i
gcc -std=c17 -S -O0 hello.c -o hello.s
gcc -std=c17 -c hello.c -o hello.o
readelf -h hello.o
readelf -S hello.o
readelf -l hello
objdump -d hello | less

hello.o 是尚未链接的目标文件；readelf -l 应用于可执行文件 hello 时，才适合观察装载用的程序头。readelf 输出中的 ELF64、机器类型、节和段，将在第 18 章 ELF 文件与第 20 章链接反复出现。

三、按原书章节学习

书中位置必须建立的关联现代实操
第 I 部分：1—13 章类型、表达式、控制流、函数、数组、算法与调试；理解“源码到底承诺了什么”。用 -std=c17 -Wall -Wextra -Wpedantic -g -O0，在GDB 章反复单步。数组越界练习额外用 -fsanitize=address,undefined 编译并链接；插桩检查只覆盖实际执行的路径。ASan 文档
第 II 部分：14—27 章数的表示、类型布局、指针、函数调用、ELF、链接、预处理、构建、库和数据结构之间的关系。第 18—19 章原始汇编先按 32 位实验；同时对一个 64 位 C 程序执行 gcc -S、readelf、objdump。保留Makefile作为依赖模型，掌握后再对照 CMake 官方教程。
第 III 部分：28—37 章文件描述符、进程、虚拟内存、文件系统、信号、线程、网络如何构成程序的运行环境。用 strace 观察库调用后的系统调用，用 ip 观察网络。ext2 是磁盘格式案例，不代表当前工作目录一定使用 ext2；对照 Linux ext4 文档和实际挂载信息。

AI 基础设施的衔接顺序：先用数组、指针、生命周期理解数据布局；再用 ABI、链接和装载理解动态库；用进程、虚拟内存、线程与文件 I/O 理解并发和数据路径；最后把同样的问题带到 GPU 运行时、通信库与服务进程。原书并不讲 GPU 或分布式训练，本页只是标出这些概念的先修关系。

四、已核实的勘误

下表对应已直接改过的书页。区分“原文有误”和“旧环境输出”：前者改正概念，后者保留原实验但补上适用条件。

位置修订原因及结果核查依据
表达式、函数、预处理原文说每个表达式都有值；void 表达式有类型，却不产生可使用的值。原文又把隐式函数声明说成会推导形参类型；C89 旧规则只假定 int 返回值、参数未知，C99 起删除该规则。WG14 C 草案、GCC 14 移植说明
数组越界访问是未定义行为；普通编译不保证诊断。增补编译器插桩检查命令。Clang ASan 文档
整型与指针宽度指针宽度取决于 ABI，不能简单等同处理器位数；原文关于有符号数表示法的说法限定在旧标准，C23 已要求补码。GCC x86 选项、GCC 整数实现
32 位汇编、声明与链接旧汇编命令补 as --32 和 ld -m elf_i386；跨源文件函数必须有正确原型，不能依赖隐式声明。GNU as 手册、GCC 14 移植说明
线程原文误写 thread_t 并把 pthread_t 断言为地址；改为实现相关的标识符说明，编译命令用 -pthread。POSIX pthread_equal、GCC 链接选项
IPv4 地址与路由原文 E 类上界 247.255.255.255 是笔误；保留旧输出并补 ip 命令。IANA IPv4 注册表
